# Контракт расширенной модели

С версии 0.2.0 OpenDoc Model расширяет общую модель документа типизированными данными и
операциями, независимыми от внешних форматов и приложений. API описан в
[руководстве](../guide/integration.md); реализация находится в
[типах](../../src/opendoc_model/integration_types.py) и
[операциях](../../src/opendoc_model/integration.py). Обязательные зависимости и
версии сохранённого документа не изменены.

| Область | Реализация и границы |
| --- | --- |
| Профили возможностей и сохранение | FeatureCapability, CapabilityProfile, PreservationRecord; существующие DiagnosticIssue/CheckResult/Provenance; неполный отчёт не подтверждает lossless |
| Исходные позиции и неизвестные фрагменты | SourceMap/File/Span/Mapping, ссылки раскрытий, digest, UnknownFragment с resource ID, media type и конечным размером |
| Поля и диапазоны | Существующие Anchor ID, TextPosition/Range, Field/BibliographyEntry, Comment/Revision/ContentControl; Unicode-редактирование и проверка ссылок |
| Векторные данные | Paths/Paint/AffineTransform/Groups/clip/mask/z-order, пункты и ColorValue; арность, конечные числа, циклы и бюджеты |
| Диаграммы и стили | Chart/Series/Axis, Diagram, явное наследование SceneStyle и отдельный visual fallback |
| Страницы и дополнительные данные | Pages/reading order/accessibility, annotations/forms, inert actions, media/timing; Workbook/Sheet/Cell отдельно от Table |
| Структура математики | FormulaTree/MathNode рядом с существующей Formula и исходными ресурсами; арность, глубина и число узлов |
| Развитие схем | Explicit consumer ExtensionMigration, forward chains, schema validation, atomic failure, feature negotiation, unknown-field preservation |

Данные подключены к существующим JSON-конвертам и валидации. Дополнительная
схема имеет собственную версию 1; JSON документа продолжает записываться в версии
2 и читаться в версиях 1 и 2. `Block` включает Paragraph, Table, Formula и Image;
новые произвольные типы структурных узлов не вводятся.

Проверки находятся в [корпусе](../../tests/test_integration.py): восстановление
JSON, Unicode и cross-run ranges, исходные spans, зависимости при извлечении,
переназначение IDs при объединении, повреждённые ссылки, циклы, неизвестные версии,
квоты и отсутствие частичных изменений.
[Пример](../../examples/integration_model.py) исполняется проверкой сайта и
установленным wheel без зависимостей. Сохранённые контракты API и JSON 0.1.0
остаются отдельными проверками совместимости.

## Назначение и пределы

Библиотека хранит, изменяет, сериализует и проверяет структуры в памяти. Конечная
схема задаёт общий носитель данных и не гарантирует чтение полного стандарта
документа. Чтение внешних файловых форматов, вычисление формул, поля, actions,
отрисовка, OCR, UI и редакторская история находятся вне API ядра.

Неподдержанные команды и исходные байты сохраняются через PackageGraph, Resource,
UnknownFragment или extra. Сохранение непрозрачных данных не означает понимание
их семантики. Профили и отчёты описывают заявленный охват потребителя. Библиотека
не выполняет скрипты, макросы, формулы и команды из сохранённых данных, не
открывает URI автоматически и не подключает внешние движки.

## Развитие публичного контракта

Модель владеет независимыми структурами, собственными JSON-схемами, их явными
миграциями, валидацией и сравнением. Преобразование внешнего формата, работа
нативного движка и форматная диагностика принадлежат адаптеру. Прикладные
сценарии, шаблонная политика, очереди и выбор бюджета качества принадлежат
потребителю. Геометрические декларации не становятся движком компоновки,
а исходные ресурсы и provenance — обработчиком файлов.

Новое требование к модели должно содержать точную версию и вызывающий API,
собственный разрешённый fixture с происхождением, вход и ожидаемую модель/JSON,
публичную сигнатуру и результат, диагностику, лимиты и поведение отказа,
совместимость прежних JSON и конечную проверку двух циклов. Для новых полей
нужны правила чтения, валидации и сравнения; отсутствие измерения остаётся
неизвестным. Выпуск нового API не подтверждает его поддержку внешним адаптером:
потребитель отдельно проверяет совместимые официальные пакеты и их контрольные
суммы, без подмены установленного пакета исходниками.

Выполненные работы описаны ниже и в [завершённых возможностях](completed.md).
Активного TODO нет; форматные и прикладные задачи в него не переносятся.

## Рассматриваемое расширение: границы таблиц и ячеек

Дата рассмотрения: 10 октября 2026, проверенная версия — 0.7.2. Публичных
типизированных границ таблиц/ячеек нет. `Paint` и `VectorPath.stroke` относятся
к векторной сцене и не задают стороны табличной рамки или наследование.
Произвольные свойства сохраняют JSON, но не обеспечивают проверку и сравнение
семантики границ. Сообщённая потеря прямого оформления во внешнем цикле —
свидетельство потребителя, а не самостоятельно воспроизведённый дефект ядра.

Рассматриваемый контракт должен описывать:

- стороны top/left/bottom/right, внутренние горизонтальные/вертикальные линии
  таблицы и две диагонали ячейки с явно определёнными направлениями;
- вид линии, существующий `ColorValue`, толщину и отступ в пунктах,
  конечные допустимые значения и неизвестное/неподдержанное оформление;
- различие отсутствующего объявления, явного отсутствия линии и сброса;
  исходные none/nil не должны молча превращаться в одно значение без правил;
- приоритет прямой декларации над явно заданным наследованием, независимые
  правки отдельных сторон и удаление без восстановления прежней декларации;
- собственную версию JSON, валидацию владельца/сторон/значений, сохранность
  неизвестных полей, атомарный отказ и существующие бюджеты;
- сравнение деклараций и диагностику утраты без обещания вычисленной
  компоновки, разрешения конфликтов соседних границ или внешнего отображения.

До реализации требуется собственный разрешённый fixture, точная ожидаемая
модель/JSON, публичные сигнатуры, правила чтения прежних документов и конечная
проверка двух циклов, включая прямую правку, наследование и удаление.
Нативное извлечение/запись, движки и проверка внешнего результата принадлежат
адаптеру. Новый API пока не объявлен; версия и опубликованный пакет не меняются.

## Реализованный контракт: оглавление и закладки

С 0.7.0 `Outline`, `OutlineEntry` и `OutlineTarget` задают устойчивые ID,
parents, порядок среди соседей и назначения anchor/page/external.
[Публичный контракт](../guide/outline.md) определяет неизвестное назначение,
исходные координаты страницы, zoom как долю, происхождение и инертные URI.

Tagged-схема v1 лежит в IntegrationModel.extra; прежние конструкторы,
integration v1 и JSON документа v1/v2 сохранены. Неизвестные поля сохраняются;
будущие версии, коллизии ключа, неверные ссылки, циклы и дубли дают отказ.
Плоское хранение не снимает ограничения глубины родителей.

Merge переписывает anchor-назначения выбранного целиком конверта. Entry/page
ID сохраняются вместе с его pages; автоматическое объединение двух оглавлений
не вводится. Явный remap поддерживает отдельные карты entry/anchor/page,
проверяет иерархию и уникальность. Extract сохраняет записи и замыкает
внутренние назначения, при необходимости добавляя целые секции. Структурные
правки не оставляют висячие ссылки. Частные extra-поля не ремапятся автоматически.

[Сценарии](../../tests/test_outline.py) проверяют JSON, Unicode titles,
provenance, unknown fields, карты ID, композицию, ссылки и атомарные отказы.
[Пример](../../examples/outline.py) исполняется документацией и независимым wheel.
Native parsing, автоматическое оглавление по стилям, отображение и выполнение
переходов остаются вне назначения библиотеки.

## Реализованный контракт: геометрия страницы

С 0.6.0 `PageGeometry` явно задаёт исходную media-область, crop и поворот
0/90/180/270 градусов. [Контракт](../guide/page-geometry.md) определяет
координаты в пунктах, порядок переноса/поворота и обратные преобразования
точек/прямоугольников. Legacy width/height остаются размерами исходной
media-области; Box и поворот элемента автоматически не переинтерпретируются.

Схема v1 хранится в неизвестных полях DocumentPage; integration v1,
JSON документа v1/v2 и прежние конструкторы сохранены. Старый reader сохраняет
декларацию непрозрачно. Проверяются конечные координаты/границы, положительные
области, вложенность crop и размеры страницы. Непрозрачные коллизии и будущие
версии дают отказ; unknown fields и бюджеты проверяются до возвращения новой
страницы. set_integration остаётся атомарным.

[Сценарии](../../tests/test_page_geometry.py) проверяют четверть-обороты,
ненулевую обрезку, обратимость, JSON, композицию, аннотации и отказы.
[Пример](../../examples/page_geometry.py) исполняется документацией и wheel
без сторонних зависимостей. С 0.7.0 page-назначения оглавления используют
исходные координаты страницы; преобразование в область отображения выполняется
явно. Native parsing, clipping и rendering не добавлены.

## Реализованный контракт: предпочтительная ширина

С 0.4.0 доступны `WidthMeasure`, `get_preferred_width` и `set_preferred_width`
для таблиц и ячеек. [Публичный контракт](../guide/styles.md#предпочтительная-ширина-таблиц-и-ячеек)
определяет единицы, базу доли, auto/unspecified, приоритет явных правок и
совместимость legacy `width_twips`. Grid и измеренная геометрия остаются отдельными
данными. Доли выше 1 разрешены, для вложенной таблицы content означает доступную
область содержимого её контейнера. Ядро не вычисляет размер этой области.

Конечный собственный случай 20×3 сохраняет предпочтительную ширину таблицы
480 pt, сетку 48/384/48 pt и относительные ширины ячеек 10/80/10 процентов.
Два JSON-цикла, provenance, неизвестные поля, валидация, сравнение, композиция,
совместимость старых JSON и атомарные отказы закреплены в
[test_widths.py](../../tests/test_widths.py). Публичный пример
[table_widths.py](../../examples/table_widths.py) выполняется документацией и
независимым wheel без сторонних зависимостей.
JSON документа v1/v2 и bags v1 сохранены. Фактическая ширина и число страниц
без внешнего измерения остаются неизвестными; нативный разбор и компоновка
находятся вне API библиотеки.

## Реализованный контракт: семантика таблиц

С 0.5.0 доступны `TableSemantics`, `TableRowSemantics`, `TableCellSemantics`,
`TableRowGroup`, `TableColumnGroup` и публичные getters/setters.
[Контракт](../guide/table-semantics.md) задаёт владение форматированной подписью,
роли header/data, row/column/row-group/column-group scope и явные headers.
Таблица и абзацы подписи используют существующие якоря; ID строк, ячеек и
групп локальны для таблицы. Разные body-группы сохраняются отдельно.

Конечные tagged-схемы v1 лежат в properties. JSON документа v1/v2, bags v1 и
прежние конструкторы сохранены. Непомеченные данные остаются непрозрачными;
частные форматные поля не мигрируют автоматически. Неизвестные поля записей
сохраняются в extra, без исполнения или обещания понимания.

Валидация проверяет владельца/тип подписи, ID и локальные headers, циклы,
scope, группы и интервалы spans с явным бюджетом. Merge переназначает якоря,
extract замыкает зависимости подписи/владельца либо отклоняет неполную таблицу.
Невалидные структурные правки откатываются; сравнение сообщает утрату деклараций.
Происхождение таблицы/абзацев и существующая языковая Accessibility сохраняются
их прежними структурами, без новой модели исходного формата.

Приёмка закреплена в [test_table_semantics.py](../../tests/test_table_semantics.py):
форматированная подпись с локальным языком, два JSON-цикла, заголовки колонок,
строки и групп, IDs/headers, две body-группы и rowspan, повреждённые связи,
merge/extract, сравнение, старый JSON, лимиты и неизменность при отказе.
[Пример](../../examples/table_semantics.py) исполняется документацией и wheel
без зависимостей. Чтение/безопасный вывод HTML, полная ARIA и внешняя приёмка
экранным диктором остаются вне API модели.
