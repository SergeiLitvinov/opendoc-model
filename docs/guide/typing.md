# Проверка типов

Производственные модули `src/opendoc_model` проверяются mypy 2.4.0 в строгом режиме:

```text
uv sync --all-extras
uv run mypy
```

Конфигурация `pyproject.toml` включает все модули библиотеки, задаёт Python 3.11,
включает `strict` и размещает кэш в `.opendoc/mypy-cache`. CI запускает тот же
прогон на Python 3.11/3.12/3.13. В конфигурации нет общего отключения ошибок,
пропуска импортов или анализа производственных модулей. Проверка CI настроена;
локальный успешный прогон не является свидетельством уже выполненного удалённого CI.

`mypy` — зависимость разработки. Основная установка OpenDoc Model
по-прежнему не требует сторонних пакетов. Аннотации optional XML проверяются
с собственными stubs из `tools/typing/lxml/`, а сам `lxml` загружается лениво
при вызове нужной функции. Stubs описывают только используемый API, не всю
стороннюю библиотеку; они не исполняются и не поставляются в wheel.
Типы, нужные только анализатору, не должны создавать runtime-зависимости.
Версии инструментов фиксируются в `uv.lock`.

## Что проверяется

Модель, обход, изменения, композиция, ресурсы и стили имеют конкретные типы
узлов/ссылок. Цветовые kwargs описывают именованные поля вместо произвольного
`object`. `ObjectMatch` задаёт поля результата сопоставления; `TextFlowData`
задаёт структуру текстового отпечатка. Они остаются обычными словарями при
исполнении. Подсчёты выделения и состояния политик имеют конкретные типы;
возможная недоступность учитывается как `None`, а отсутствующее сравнение
проверяется до обращения к его полям.

Методы `to_dict()` возвращают публичные `TypedDict`:

| Результат | Тип словаря | Статически проверенные поля |
| --- | --- | --- |
| `DocumentInspection` | `InspectionData` | Флаги, nullable путь, строковый формат, целочисленные метрики/счётчики, список диагностик |
| `DocumentComparison` | `ComparisonData` | Флаги, числовые или неизвестные значения retention/geometry summary, число совпавших хешей, диагностики |
| `CheckResult` | `CheckData` | Формат, версия, флаги, диагностики `DiagnosticData` с nullable reason/measurement |
| `ConversionReport` | `ConversionReportData` | Путь результата, флаги и диагностики `ConversionIssueData` |

Все шесть типов экспортируются из `opendoc_model` и `opendoc_model.result_types`.
Они описывают существующие словари, не создают отдельные runtime-классы
результатов и не меняют JSON документа или проверки `opendoc.check` v1.
Публичные `ObjectMatch` и `TextFlowData` доступны в своих модулях.
Сохранённый контракт `tests/fixtures/compatibility/api-0.1.json` проверяет
их обязательные/необязательные ключи, типы полей, корневые реэкспорты и
возвращаемые типы четырёх методов `to_dict()`. Он дополняет проверку прежних
параметров, defaults и идентичности классов.

Статическая проверка не заменяет [валидацию модели](validation.md),
[JSON-проверку](json.md) и [вычислительные лимиты](performance.md).
Она проверяет использование заявленных типов в анализируемом коде, но не
запрещает вызывающему Python-коду передать другой объект во время исполнения.
Публичные параметры, defaults, классы и версии JSON сохраняются.

## Динамические границы

`Any` остаётся у JSON-входов, произвольных metadata/properties, расширяемых
метрик и XML-представления optional backend. Это явные границы, где потребитель
может передавать данные с собственной схемой. Строгий прогон с такими границами
не доказывает тип каждого вложенного ключа. Нужную схему проверяют библиотечные
валидаторы или [явные валидаторы расширений](extensions.md).

Классы `DocumentInspection`, `DocumentComparison` и `CheckResult` задают основные
результаты API. Конверты их словарей типизированы; вложенные записи объектов,
ресурсов, страниц, геометрии и format-dependent сравнений остаются открытыми.
Метрики `CheckResult`/`ConversionReport` допускают собственные политики
потребителя. Тип конверта не доказывает схему всех вложенных измерений.
Наличие `py.typed` в пакете означает доступность
аннотаций потребителю; оно само по себе не доказывает их полноту или корректность.

Аудит оставшихся явных `Any` охватывает следующие границы:

| Модули | Причина динамического типа |
| --- | --- |
| `document_model`, `properties`, `extensions` | Сохраняемые metadata/properties и данные схем потребителя; ключ `get_typed` выбирается во время исполнения |
| `document_codec`, `_json_validation`, `color` | Чтение неизвестного JSON и проверка перед восстановлением модели |
| `_validation`, `semantics`, `lists`, `references`, `footnotes` | Проверка повреждённых данных и tagged properties; чтение сохранённых JSON-инвентарей |
| `inspection`, `object_inventory`, `object_matching`, `result_types` | Открытые JSON-записи инвентаря и измерений; фиксированные поля конвертов проверяются отдельно |
| `diagnostics`, `emphasis_quality`, `text_edit_budget` | Расширяемые отчёты и проверяемые словари отпечатков/измерений |
| `_xml`, `mathml`, `formula_quality_policy` | Дерево лениво загружаемого XML-бэкенда и его JSON-отпечаток |

Узлы модели, операции обхода, счётчики, состояния политик и ключи внутренних
индексов не заменены `Any`: используются типы узлов, чисел, nullable значений
и `Hashable`. Проверка бюджета принимает `object`, затем разбирает контейнеры
и dataclass-поля. Динамические входы валидируются при исполнении; mypy не
гарантирует тип результата произвольного потребительского валидатора.

## Потребитель установленного пакета

После сборки и установки wheel без зависимостей в отдельное окружение:

```text
uv run python -m tools.check_wheel --python <путь-к-python-окружения-wheel>
uv run python -m tools.check_types --python <путь-к-python-окружения-wheel>
```

В CI оба прогона выполняются на Python 3.11/3.12/3.13. Анализатор работает
из окружения разработки, а `--python-executable` указывает окружение только
с установленным OpenDoc Model. `tools.check_types` копирует fixtures из `tests/typing`
во временный каталог, исключает `MYPYPATH`/`PYTHONPATH`, проверяет путь импорта,
наличие `py.typed` и отсутствие других установленных дистрибутивов.

Положительный сценарий использует модель, JSON, обобщённый обход, цвета,
инспекцию, сравнение, проверки, диагностики и текстовый отпечаток. `assert_type`
проверяет конкретные типы и nullable значения; тот же сценарий исполняется
Python установленного wheel. Отрицательный сценарий содержит восемь ошибок
аргументов и присваиваний полям результатов. Проверка требует ошибки ровно
на отмеченных строках и с ожидаемыми кодами; этот сценарий не исполняется.
Контрольный прогон с `--no-site-packages` обязан потерять импорт OpenDoc Model:
успех за счёт исходников checkout не принимается.

Использование установленного typed-пакета описано в
[документации mypy](https://mypy.readthedocs.io/en/stable/installed_packages.html).
Собственные XML-аннотации проверяются позитивным и негативным сценарием
`tests/test_xml_typing.py`; новые обращения к XML API требуют уточнения этого
локального контракта. Общее подавление ошибок импортов не используется.
