# Межстрочный интервал

С версии 0.12.0 `LineSpacing` задаёт независимую декларацию интервала абзаца.
Это правило компоновки, а не измеренная высота глифа, строки или страницы.
Библиотека хранит, разрешает и сравнивает объявления; она не рассчитывает
нативный каскад, метрики шрифта, clipping или результат отображения.

## Правило и единицы

| Декларация | Значение |
| --- | --- |
| `LineSpacing("minimum", 14)` | Минимальный шаг строк 14 pt; естественные метрики могут потребовать большего |
| `LineSpacing("exact", 14)` | Фиксированный шаг строк 14 pt независимо от естественных метрик |
| `LineSpacing("relative", 1.5)` | Множитель 1.5 естественного шага строки; не 1.5 pt и не множитель размера шрифта |
| `LineSpacing()` | Явное неизвестное правило/значение; блокирует fallback |
| Нет декларации | Разрешено наследование; отсутствие по всей цепочке остаётся неизвестным |

`rule` и `value` известны вместе или оба равны `None`. Известное значение
строго положительно и конечно; ноль, отрицательные числа, bool, строки, NaN
и бесконечности отклоняются. Пункты — 1/72 дюйма. Естественные метрики для
relative и minimum определяет потребитель; модель не подставляет single,
нормальный размер шрифта или другие скрытые defaults.

## Владельцы и наследование

`get_line_spacing` и `set_line_spacing` работают с `Paragraph` и `TextStyle`.
Именованный стиль абзаца может нести эту декларацию в своих properties.
`resolve_line_spacing(paragraph, document=document, inherited=fallback)`
применяет приоритет **прямая декларация → цепочка paragraph.style_id/base_style_id
→ явно переданный fallback**. Каждая декларация заменяет предшествующую целиком.
Документ обязателен при ссылке на стиль; неизвестная ссылка и цикл — ошибки.
Автоматического стиля по умолчанию нет: потребитель явно задаёт style_id или fallback.

У `TextStyle` resolver использует прямую декларацию и base_style_id.
Существующий `resolve_style` также переносит tagged-свойство через модельную
цепочку. Интервал — свойство абзаца: стиль отдельного TextRun не меняет результат
resolver или paragraph inventory, даже если он транспортирует декларацию.
`effective_text_style` с run не служит resolver интервала абзаца.

```python
from opendoc_model import LineSpacing, set_line_spacing, resolve_line_spacing

set_line_spacing(paragraph, LineSpacing("exact", 18))
assert resolve_line_spacing(paragraph, document=document).value == 18
set_line_spacing(paragraph, None)  # удалить прямое объявление, снова разрешить стиль
```

Getter и resolver возвращают независимые значения. Setter сохраняет неизвестные
поля предыдущей декларации; `dataclasses.replace` подходит для правки записи.
Удаление убирает объявление вместе с его расширениями. Ошибка формы, версии,
владельца или лимита не меняет исходный объект. Все операции принимают
`DocumentLimits`; явно увеличенный бюджет передаётся внутреннему кодеку.

## JSON и старые свойства

Схема лежит в `properties["opendoc.line-spacing"]`, имеет одноимённый format
и version 1. Документ по-прежнему читается в v1/v2 и пишется в v2;
конструкторы, property bags, integration и зависимости сохранены. Неизвестные
поля проходят два JSON-цикла и доступны через `extra`; они не исполняются.
Поля схемы и format/version нельзя подменить через extra. Tagged-схема неизвестной
версии вызывает ошибку. Непомеченное содержимое ключа остаётся непрозрачным;
getter возвращает None, setter отказывается его перезаписывать или удалять.
Явный fallback не интерпретирует это содержимое.

Старые `line_spacing`, `line_spacing_pt` и форматные правила, включая
`docx_line_spacing_rule`, сохраняются как прежде. Их числовые представления
доступны прежнему PropertyBag API, но не задают новое общее правило и не мигрируют
автоматически. Сопоставление нативных minimum/exact/relative и единиц выполняет
потребитель явно. После такой миграции сравнивается общий контракт; оставшиеся
нативные свойства не становятся доказательством его сохранности.

## Сравнение и пределы проверки

`inspect_document_model` добавляет `line_spacing` с `direct` и `resolved`;
снимки содержат только известные rule/value, без интерпретации extra.
Изменение числа, minimum → exact или exact → relative даёт расположенное
`line-spacing-change` (WARNING). Удаление прямого объявления, даже при том же
значении стиля, или известное → явно неизвестное даёт `line-spacing-loss` (LOSS).
Изменение используемого именованного стиля тоже видно у соответствующего абзаца.
`DiagnosticIssue.measurement` содержит source/target; `QualityPolicy(0)`
отклоняет LOSS. Сравнение проверяет объявление и разрешённый модельный результат,
а не равнозначность разных правил при конкретном шрифте.

`compare_inspections(...).object_diff["line_spacing_available"]` сообщает полноту
этой области; у `compare_documents` это
`metrics["comparison"]["object_diff"]["line_spacing_available"]`.
Старый/повреждённый inventory, отсутствующий контекст именованных стилей и
непрозрачные старые свойства без принятой декларации делают область недоступной.
Известные пары абзацев сравниваются и в частичном профиле; false не скрывает их
замечаний. Отсутствие issues при недоступной области не подтверждает сохранность.

[Собственный пример](../../examples/line_spacing.py) проверяет наследование,
правки и два JSON-цикла всех трёх правил. [Тесты](../../tests/test_line_spacing.py)
покрывают удаление, неизвестное, цепочки, JSON v1/v2, композицию, расширения,
лимиты и атомарность. Нативное чтение/запись и визуальная приёмка остаются
ответственностью потребителя; библиотечный аудит не объявляет их выполненными.
