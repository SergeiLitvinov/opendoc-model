# Стоимость операций

Воспроизводимый сценарий [tools/performance.py](../../tools/performance.py)
измеряет обход, JSON/base64, инспекцию вложенных таблиц и сопоставление дубликатов:

```text
uv run python -m tools.performance --sizes 128 512 2048 --repeats 3 --output .opendoc/performance.json
```

Отчёт содержит размеры входов, все временные выборки, медиану, пик выделений
`tracemalloc` и среду. Перед измерением выполняется один прогрев; сборка мусора
проходит до запуска таймера. Память измеряется отдельным запуском, чтобы трассировка
не искажала опубликованное время. Пик отражает выделения Python внутри операции,
а не RSS процесса, размер заранее созданного входа или абсолютный расход памяти.
`--source-root путь/к/src` позволяет повторить тот же сценарий со старым checkout.
Результаты зависят от машины и нагрузки; это наблюдения, а не гарантии задержки.

## Измерение индексов до введения бюджета

Дата: 2026-10-03. Python 3.12.13, Windows 11 10.0.26300, AMD64, OpenDoc Model 0.1.0.
Для обхода и инспекции N означает число абзацев с отдельным текстовым фрагментом.
Вложенность таблиц — 8: все абзацы расположены в самой глубокой ячейке.
Для JSON встроены N KiB байтов одного ресурса; для сопоставления имеются N
исходных и N конечных объектов с одинаковым content hash. Целевой список
дубликатов развёрнут; в сценарии конфликтов все явные origins различны
в рамках одного формата и пути источника.

| Операция | N=128, мс | N=512, мс | N=2048, мс | Пик при N=2048, MiB |
| --- | ---: | ---: | ---: | ---: |
| Обход плоского документа | 2,759 | 10,689 | 42,090 | 0,838 |
| JSON/base64 запись | 1,123 | 4,163 | 16,064 | 7,343 |
| JSON/base64 чтение | 8,752 | 31,894 | 118,186 | 7,342 |
| Инспекция вложенных таблиц | 19,466 | 72,375 | 430,541 | 4,760 |
| Сопоставление дубликатов | 0,265 | 1,048 | 4,265 | 1,408 |
| Сопоставление конфликтующих origins | 1,052 | 4,049 | 30,196 | 1,983 |

При N=2048 ресурс содержит 2 097 152 байта; JSON занимает 2 796 592 UTF-8 байта.
Отчёты этого запуска: `.opendoc/performance-l16-before.json` и
`.opendoc/performance-l16-current.json`; они являются локальными артефактами.

До индекса кандидатов, на исходном коде коммита `02cb738`, сопоставление
2048 дубликатов занимало 433,736 мс с пиком 0,930 MiB; конфликтующих origins —
1585,326 мс с пиком 1,223 MiB. Индекс ускоряет эти сценарии ценой дополнительной
памяти. Он сохраняет прежний порядок фаз, предпочтение равного расположения,
первого совместимого кандидата и признак неоднозначности; одинаковые отпечатки
не объединяются в один объект. Индекс применяется к группам одного источника
и группам явного provenance. Смешанные источники используют прежний поиск
совместимых кандидатов; общая линейная сложность не заявляется.

## Содержимое таблиц

В рамках одного вызова инспекции содержимое узла вычисляется один раз и
переиспользуется для вложенных таблиц. Кэш не переживает операцию: изменение
модели перед следующим вызовом учитывается. Повторные вхождения остаются
отдельными объектами, отдельно пополняют счётчики и текстовый поток. Неизвестное
содержимое, например изображение без встроенных байтов, остаётся неизвестным.

Устранение повторных вычислений подтверждено тестом вложенных и разделяемых
узлов с сохранением ожидаемых хешей. Полное время инспекции в опубликованном
запуске не уменьшилось: до изменения при N=2048 оно составляло 285,658 мс.
Инспекция включает валидацию, семантические инвентари и другие обходы;
удаление повторного вычисления содержимого само по себе не доказывает
ускорение всей операции. Рост пика с 4,514 до 4,760 MiB отражает хранение кэша.

[Лимиты документа](limits.md) ограничивают входную глубину, число значений,
размер JSON и встроенные байты. Они не являются лимитом времени выполнения.

## Бюджет сопоставления

`MatchingLimits(max_work=1_000_000)` задаёт отдельный неотрицательный целочисленный
бюджет работы. Он передаётся через `compare_documents(..., matching_limits=...)`
и `compare_inspections(..., matching_limits=...)`. В прямом API
`opendoc_model.object_matching.match_objects` аргумент называется `limits`.
`None` выбирает тот же конечный бюджет по умолчанию, а не отключает ограничение.
Пустое сопоставление допускает нулевой бюджет. Пример отказа и успешной проверки —
[examples/matching_limits.py](../../examples/matching_limits.py).

Единица работы — просмотр/индексация записи или кандидата. Учитываются размеры
входов до выделения начальных множеств, обходы оставшихся записей в пяти фазах,
обработка групп, построение индексов, выбор и удаление устаревших кандидатов,
проверки совместимости/расположения, создание пар и окончательных списков.
Массовые проходы заряжаются заранее; отдельный шаг запрещается до его выполнения,
если он не помещается в остаток. Это детерминированный алгоритмический бюджет,
а не таймер, число инструкций CPU или обещание максимального RSS. Он не ограничивает
валидацию/инспекцию модели или стоимость обработки длинных строк; бюджеты
представления задаются отдельно через `DocumentLimits`.

Один бюджет используется последовательно для объектов, определений/ссылок якорей
и определений/ссылок сносок. Неизрасходованный остаток доступен следующей области.
Уже завершённая область сохраняет результат, а область, не завершившаяся в бюджете,
возвращает `available=False`, `reason="matching-budget-exceeded"` и
`matching_budget` с `max_work`, `used_work`, `requested_work`. Частичные пары,
потери и изменения не выдаются за полное измерение: списки остаются пустыми,
неизмеренные счётчики/ratio — `None`.

Прямой matcher вызывает `ArtifactLimitError`. Сравнение перехватывает только
исчерпание этого бюджета и добавляет INFO `object-matching-unavailable`,
`reference-matching-unavailable` или `footnote-matching-unavailable`.
`compare_documents` также даёт машинную причину в `measurement.unavailable`.
Неверные настройки вызывают `ValueError`. Без выбранной политики недоступность
не становится ERROR; это не доказательство сохранности. Строгая `ObjectLossPolicy`
при неизвестном сопоставлении объектов отказывает с `reason="unavailable"`
и `lost_objects=None`. Независимые измерения текста, ресурсов или геометрии
сохраняются, если их собственные условия выполнены.

При достаточном бюджете порядок фаз, выбор пар и неоднозначность остаются прежними.
Увеличение бюджета — явное решение потребителя; неизвестность не заменяется
предположением о потерях. JSON документа v2, чтение v1/v2 и bags v1 не изменены;
новые необязательные аргументы и класс закреплены как дополнение публичных контрактов.

## Измерение смешанных источников

Тот же сценарий теперь включает `match-mixed-sources`: N исходных записей одного
источника и N конечных записей, половина которых принадлежит другому формату.
Все content hashes равны, явные идентификаторы исходных и конечных записей различны.
Прежний алгоритм полностью сопоставляет половину вхождений; они неоднозначны.
Замеры выполнены тем же методом и в той же среде; локальные отчёты:
`.opendoc/performance-l16-old-mixed.json` и `.opendoc/performance-l16-budget.json`.

| Размер каждой стороны | Прежний matcher, мс | Matcher с бюджетом, мс | Пик с бюджетом, MiB | Результат с бюджетом |
| ---: | ---: | ---: | ---: | --- |
| 128 | 4,027 | 5,577 | 0,087 | 64 пары, 64 потери, 64 добавления |
| 512 | 57,396 | 77,421 | 0,334 | 256 пар, 256 потерь, 256 добавлений |
| 2048 | 946,131 | 500,128 | 1,224 | Недоступно: использованы 1 000 000 единиц |

500,128 мс при N=2048 — время остановки, а не время полного сопоставления.
Дополнительный учёт имеет стоимость; смешанный поиск не объявляется линейным.
В этом запуске индексированные 2048 дубликатов занимали 8,731 мс с пиком
1,408 MiB, конфликтующие origins одного источника — 38,500 мс с пиком 1,983 MiB.
Границы, общий бюджет областей, отсутствие частичных потерь, отказ строгой политики
и сохранность дубликатов проверяются отдельно от нестабильных временных порогов.
