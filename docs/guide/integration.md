# Расширенная модель документа

`IntegrationModel` — типизированное дополнение к общей модели OpenDoc Model для
потребителей библиотеки. Все типы доступны из `opendoc_model`. Данные сохраняются в `document.metadata['opendoc.integration']` с
отдельной версией схемы **1**. Версия JSON документа остаётся **2**; старые схемы
документа 1 и 2 читаются. Старые читатели сохраняют конверт как metadata, но не
понимают его семантику. Дополнение доступно с OpenDoc Model 0.2.0;
wheel 0.1.0 его не предоставляет.

## Подключение, JSON и проверка

Для отдельного ledger без документа с 0.18.0 доступны
[`integration_to_dict` / `integration_from_dict`](integration-codec.md).
Они используют тот же конверт и типизированную схему, сохраняют независимость
данных и лимиты; существование внешних ссылок проверяется только с владельцем.

`set_integration(document, model)` проверяет типы, ссылки и бюджеты, сохраняет
независимый снимок и изменяет документ только после успешной проверки.
`get_integration(document)` возвращает независимые типизированные данные либо
`None`, если конверта нет. `set_integration(document, None)` удаляет известный
конверт. Непомеченные данные с занятым ключом нельзя молча перезаписать.

`document.validate()`, `check_document`, запись и чтение JSON проверяют известную
схему автоматически. Неизвестная версия этой схемы отклоняется; произвольные
потребительские схемы используют [явную политику расширений](extensions.md).
Неизвестные поля конверта сохраняются, а неизвестные поля типизированных записей
попадают в `extra`. Нельзя перекрывать ими поля схемы. Такие данные не становятся
семантически понятными от самого факта сохранения.

Все операции принимают `DocumentLimits`: глубина, число значений, UTF-8-объём и
встроенные байты ограничены. Циклические JSON-данные и ссылки отклоняются.
Формат не содержит имён Python-классов для динамического импорта или исполнения.

Исполняемый пример: [integration_model.py](../../examples/integration_model.py).
Полный корпус всех направлений и отказов: [test_integration.py](../../tests/test_integration.py).

## Профили и отчёт сохранения

`CapabilityProfile(id, version, features)` содержит конечный список
`FeatureCapability(feature, states, schema_version)`. `negotiate_capabilities`
возвращает пересечение состояний для каждого признака исходного профиля.
Отсутствующий признак или несовпадающая версия его схемы дают пустое пересечение.
Совпадение возможностей не доказывает успешную конвертацию конкретного файла.

`PreservationRecord` использует существующий `DiagnosticIssue`, необязательные
anchor ID и `Provenance`, а `PreservationState` различает:

| Состояние | Что сохранено |
| --- | --- |
| `semantic` | Понятная адаптеру структура в объявленном профиле |
| `opaque` | Оригинальные данные без обещания понимания и редактирования |
| `visual` | Визуальная замена без обещания семантической эквивалентности |
| `lost` | Признак потерян |
| `rejected` | Признак отклонён |

`preservation_result` возвращает существующий `CheckResult`. `lossless=True`
возможен только при явном `assessment_complete`, непустом `assessed_features`,
записи для каждого проверенного признака и исключительно `semantic`-состояниях
без диагностик LOSS/ERROR. Пустой отчёт не считается подтверждением сохранности.
Для несемантического состояния обязателен `issue.reason`; `rejected` даёт ERROR,
остальные несемантические состояния — LOSS. Это оценка адаптера относительно
заявленного охвата, а не измерение визуального качества или полного стандарта.

## Исходники и неизвестный синтаксис

`SourceMap` объединяет `SourceFile`, `SourceMapping` и раскрытия макросов.
Источник имеет URI, необязательную часть пакета, ресурс, размер и SHA-256.
URI является данными: библиотека его не открывает. SHA-256 встроенного снимка
проверяется. `SourceSpan` задаёт полуоткрытый интервал `[start, end)`, исходный
объект и связь с раскрытием. Смещения явно задаются в байтах или Unicode code
points; строка и столбец начинаются с 1. Объекты раскрытий идентифицируются через
`object_id`, ссылки `expansion_id` проверяются на существование и циклы.

Исходные позиции относятся к неизменяемому снимку исходника. Редактирование
модели не переписывает их в фиктивные позиции нового файла. Адаптер самостоятельно
строит новую source map после нового экспорта или импорта.

`UnknownFragment` ссылается на встроенный ресурс с исходными байтами и media type,
объявляет `max_bytes` и политику `preserve`, `visual` или `reject`. Visual требует
отдельного ресурса. Неизвестный синтаксис никогда не исполняется. Это типизированная
запись неизвестного фрагмента, привязанная к существующему узлу или источнику;
новые произвольные типы `Block`/`Inline` не вводятся. Исходный `Block` уже включает
`Paragraph | Table | Formula | Image`, а `Inline` — `TextRun | Formula | Image`.

## Идентичность, диапазоны и поля

Стабильные ID используют существующий `Anchor`: задайте его через `set_anchor`.
ID принадлежит документу и сохраняется при JSON и копировании; путь `NodeLocation`
и порядковый ID исходного пакета не являются заменой этой идентичности.

`TextPosition` ссылается на anchor текстового `TextRun`, содержит смещение в
Unicode code points и affinity `before`/`after`. `TextRange` имеет собственный ID,
включительное начало и исключительный конец, может охватывать несколько runs.
Порядок концов проверяется в общем порядке обхода модели, включая колонтитулы.

`edit_anchored_text(document, node_id, start, end, text)` возвращает независимую
копию с пересчитанными концами диапазонов. Концы до замены остаются на месте,
после неё сдвигаются, внутри замены переходят к её началу или концу согласно
affinity. Affinity определяет и положение курсора при вставке. Если удаление
сворачивает диапазон и переставляет его границы, он схлопывается в конечную точку.
Общий `transform_elements` отказывает при изменении текста с привязанными концами
диапазонов; прямые изменения dataclass остаются ответственностью вызывающего кода.
Простая валидация границ не может доказать правильность вручную изменённых offsets.

`Field` представляет литерал, ссылку, цитату, номер страницы, дату или custom-поле;
`BibliographyEntry` хранит заголовок, авторов и идентификаторы. Ссылки используют
anchor ID, цитаты — ID библиографии. `Comment` поддерживает ответы, `Revision`
хранит insert/delete/format и исходный текст, `ContentControl` — text/choice/date/
checkbox. Они ссылаются на range ID. Коды полей и содержимое контролов — данные:
вычисление полей, применение ревизий и редакторская история находятся у потребителя.

## Векторная сцена, диаграммы и стили

`VectorScene` содержит `VectorPath`, `VectorGroup`, явные корни и привязку к anchor.
Координаты и размеры — пункты, матрица `AffineTransform(a,b,c,d,e,f)` преобразует
`(x,y)` в `(a*x+c*y+e, b*x+d*y+f)`. `PathCommand` поддерживает move/line/quadratic/
cubic/close с 2/2/4/6/0 числами; подмаршрут начинается с move. `Paint` использует
существующий `ColorValue`, alpha и дополнительную opacity от 0 до 1. Поддержаны
stroke width, nonzero/evenodd fill, clip ID, ресурс маски и z-order.

`roots` задаёт явно отображаемые объекты; пустой список не означает автоматическую
отрисовку всех путей. Порядок отображения — по возрастанию z-order, затем порядок
корней/детей. Clip задаёт геометрию ссылки в координатах сцены; маска — alpha
ресурса в пределах сцены. Это контракт данных, библиотека не рисует сцену.
Экспортёр объявляет конечное поддержанное подмножество; неподдержанный blend mode,
ICC, clip, mask или command отражается в отчёте, а не исчезает молча.

`Chart` содержит bar/line/scatter/pie, серии, категории, необязательный cache,
оси и отдельный visual resource. Scatter требует x-values той же длины, что
значения y. `Diagram` ссылается на сцену и пары ID её фигур. Согласованные данные
хранятся типизированно, исходные OOXML namespaces остаются в непрозрачном пакете.

`SceneStyle` задаёт явно объявленную цепочку theme/master/layout/local через
`parent_id`. `resolve_scene_style` соединяет свойства от предка к потомку на
независимой копии. Неподключённые стили автоматически не применяются; циклы и
неизвестные родители отклоняются.

## Страницы, доступность, формы, медиа и книги

`DocumentPage` задаёт размеры и явный reading order из anchor ID.
Общий `canonical_coordinate_contract()` задаёт единицы `pt` (72 пункта на дюйм),
начало слева сверху, ось x вправо, ось y вниз; углы измеряются в градусах по
часовой стрелке. `Box` хранит положение, размеры и поворот элемента относительно
страницы. `transform_point_origin` и `transform_rect_origin` меняют начало
координат между верхним и нижним левым углом; они не выполняют поворот страницы.

### Рамка элемента и поворот Box

`Box(x, y, width, height, rotation=0)` задаёт прямоугольную рамку элемента
до его поворота, в исходной системе страницы. x/y — её верхний левый угол,
width/height — размеры до поворота. Центр равен
`(x + width/2, y + height/2)`. Положительный угол — clockwise вокруг этого
центра, в градусах, при оси y вниз; отрицательный задаёт обратное направление.
Поворот не заменяет x/y/width/height вычисленными границами.

Осевой bounding box повёрнутой рамки — отдельное измерение: минимальный
прямоугольник, параллельный осям страницы и охватывающий её четыре повёрнутых
угла. Например, рамка `Box(100, 100, 200, 20, 90)` имеет центр `(200, 110)`;
её bounding box — x=190, y=10, width=20, height=200. Хранить этот bbox вместо
исходной рамки с тем же rotation означало бы применить поворот повторно.

Исходный affine transform, отражение или native bbox могут сохраняться в
частном расширении адаптера. Такое расширение должно явно определить,
что описывает рамка размещения и как преобразуется содержимое. Если рамка
размещения выбрана по native bbox, `Box.rotation` задаёт дополнительный
clockwise поворот вокруг центра именно этой рамки; исходный угол содержимого
не переносится в него автоматически. Ядро сохраняет расширение непрозрачно
и не угадывает frame/bbox или композицию affine по частным ключам.

`PageGeometry.rotation` применяется к странице отдельно, после координат
элемента в исходной системе. Box не нормализует угол, не пересчитывает
обрезку или размер фигуры и не выполняет отрисовку. Старые JSON читаются без
перезаписи координат; для иной прежней конвенции нужна явная миграция у её
владельца, а не эвристика по значению rotation.

### Дополнительные данные страницы

С 0.6.0 [PageGeometry](page-geometry.md) явно задаёт media/crop и поворот
страницы в отдельной tagged-схеме в `DocumentPage.extra`. Legacy размеры
не переинтерпретируются; при добавлении декларации они должны совпадать
с размерами media до поворота. `Box.rotation` остаётся поворотом элемента.
Частные `extra`-поля не мигрируют автоматически. С 0.7.0 [Outline](outline.md)
задаёт иерархию и назначения anchor/page/external; точки назначения страницы
остаются в её исходной системе координат.

`Accessibility` добавляет role/alt/language существующему узлу; структура тэгов
опирается на дерево документа. `Annotation` и `FormControl` относятся к странице,
имеют необязательный `Box` и инертные action-данные. Ссылка `target` не открывается.
`MediaObject` указывает ресурс аудио/видео, poster и длительность; `Timing` задаёт
начало, длительность и зависимость `after_id` в секундах. Циклы отклоняются.
Автоматическое воспроизведение, переходы, scripts и callbacks отсутствуют.

`Workbook`/`Sheet`/`SheetCell` образуют отдельную схему книги. Индексы строк и
столбцов начинаются с 0, значения — строки, конечные числа, bool или null;
целые значения сохраняются точно, включая значения за пределами точности float;
формула — исходная строка без вычисления. Проверяются перекрытия ячеек и merged
диапазонов; дорогое сравнение ограничено `max_nodes`. Обычная `Table` не превращается
в электронную таблицу. Полный набор Excel/PDF/PPTX-функций схема не обещает.

## Математика и развитие схем

`FormulaTree` связывает существующий `Formula` с optional `MathNode` и ресурсами
оригинального LaTeX/MathML/OMML. Поддержаны identifier/number/operator/text, row,
fraction, root, script и matrix. Проверяются типы, арность, конечный размер и
глубина; исходное `Formula.value` и `VisualSurrogate` сохраняются. Парсер TeX,
раскрытие пакетов и вычисление выражений принадлежат адаптеру.

Для потребительских схем `ExtensionMigration` и `migrate_extension` задают явную
цепочку возрастающих версий. Callback получает независимый `ExtensionValue`;
изменение bag фиксируется только после всей цепочки и необязательной проверки
`ExtensionSchema`. `scope` явно выбирает metadata или properties для этой проверки;
по умолчанию используется metadata. Unknown envelope fields сохраняются. Неоднозначная цепочка,
отсутствующая версия, ошибка callback или лимит оставляют bag целым. Код callback
доверенный и явно передан вызывающим: его время и внешние эффекты не изолируются.
Миграции не запускаются чтением JSON, а данные не выбирают executable-код.

## Объединение, извлечение и ресурсы

`merge_documents` переназначает anchor/resource ID и ссылки новой схемы согласно
существующим картам конфликтов. Два integration-конверта используют существующую
явную политику metadata: по умолчанию конфликт отклоняется; keep_first/keep_last
выбирают целый конверт, не создают скрытого объединения независимых отчётов.

`extract_document` сохраняет integration metadata и замыкает её anchor/resource
зависимости. Поэтому частичное извлечение может сохранить дополнительные секции
и исходные ресурсы; оно не обрезает комментарии или source map без запроса.
`integration_resource_uses` дополняет `find_resource_uses` путями новой схемы.
`remove_resource` учитывает оба вида ссылок; переназначение проверяет тип, media
type и digest, отказ оставляет документ целым. Unknown `extra`-поля непрозрачны:
их частные ссылки не распознаются и не переназначаются автоматически.
