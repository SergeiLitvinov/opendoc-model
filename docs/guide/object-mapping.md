# Соответствие исходных объектов и результата

С версии 0.9.0 `ObjectMapping` — самостоятельная декларация соответствия
вхождений объектов. Библиотека хранит, сериализует и проверяет карту; вычисление
соответствий и подтверждение фактической публикации принадлежат вызывающему коду.
Она не читает нативные адреса, не открывает файлы и не создаёт изображения.
Собственный [пример](../../examples/object_mapping.py) использует синтетические
ресурсы и адреса, не выдавая их за результат нативного экспорта.

## Структуры

| Тип | Данные |
| --- | --- |
| `ObjectOccurrence` | Обязательный локальный `id`, известные `node_id`, `resource_id`, `Provenance`, `native_locator` |
| `NativeObjectLocator` | `format` и непустой инертный `value`; измеренный адрес в конкретном формате |
| `MappingReplacement` | `kind`: raster/vector/opaque, `resource_id`, `scope`: source/target |
| `ObjectMappingEntry` | `id`, непустые `source_ids`, `PreservationState`, `DiagnosticIssue`, `target_ids`, необязательная `replacement` |
| `ObjectMapping` | Реестры `sources`, `targets`, группы `entries`, `publication`, `output_format`, `assessment_complete`, необязательные `result_id` и `publication_issue` |

Все новые записи используют существующий `IntegrationRecord.extra` для
неизвестных JSON-полей. `PreservationState`, `DiagnosticIssue`, `Provenance`,
Anchor и Resource переиспользуются. `VisualSurrogate.resource_id` и его причина
могут служить входом для декларации замены и существующей диагностики; карта
добавляет вид представления и область ресурса, не заменяя сам surrogate.

ID вхождения — устойчивая идентичность внутри карты, не хеш содержимого или ID
ресурса. Два использования одного ресурса имеют разные occurrence ID и, если
заданы, разные anchor ID. Известный handle или provenance обязателен; отсутствие
остальных измерений записывается `None`. Самостоятельно придуманный номер страницы
или адрес объекта не подтверждает измерение. Значение native locator хранится
непрозрачно, без форматных правил, переходов и исполнения.

Группа допускает один-к-одному, один-ко-многим, многие-к-одному и многие-ко-многим.
Каждое вхождение входит не более чем в одну группу на своей стороне; объединение
задаётся списком исходных ID в одной группе, а разбиение — списком target ID.
Порядок реестров не заменяет идентичность; внутри группы порядок ID сохраняется.
Циклические цепочки между группами не вводятся: source/target — разные области.

## Неизвестное, потеря и публикация

`target_ids=None` означает неизвестный результат. Пустой tuple `()` означает
подтверждённое отсутствие выходных объектов и разрешён только для lost/rejected.
Непустой tuple ссылается на известные target occurrences. Lost/rejected не
объявляют выжившие объекты. Raster replacement никогда не допускает semantic:
визуальная копия не подтверждает сохранение редактируемого вектора.

Состояния semantic/visual/opaque/lost/rejected и машинная диагностика уже
определены библиотекой. Для несемантического состояния обязателен `issue.reason`;
код причины не извлекается из текста. Semantic несовместим с диагностикой
LOSS/ERROR. Validity карты не является автоматической оценкой fidelity или
разрешением политики качества.

`publication` различает unknown, attempted, staged, published, rejected и
invalidated. Staged описывает созданный промежуточный результат, published —
заявленную окончательную публикацию. Только эти два состояния допускают реальные
target occurrences и известные `target_ids`, включая подтверждённое отсутствие.
Для них нужен непустой `output_format`;
формат target locator совпадает с ним. У попытки target остаётся unknown,
созданная промежуточная замена может ссылаться на source-снимок. Target-scoped
ресурс не объявляется до материализации результата. Поле published — заявление адаптера,
не проверка файла библиотекой; источник доказательства хранится в provenance
и известных адресах. Отмена и атомарная публикация нативного файла принадлежат
его обработчику, а операции модели не выполняют файловой записи.

`assessment_complete=False` не означает отсутствия замен или успешной проверки.
True допускается для staged/published карты с непустым реестром sources,
полным покрытием **объявленных** source/target occurrences группами и известным
результатом каждой группы. Для visual нужна объявленная replacement.
Это полнота области карты, не доказательство охвата всего документа или всех
признаков. Пустая карта и отсутствие карты в прежних отчётах остаются неизвестными.

## Жизненный цикл результата

`result_id` — необязательная устойчивая идентичность конкретного результата,
независимая от имени или пути файла. Неизвестная идентичность остаётся `None`.
Повторный экспорт получает новую идентичность и новую карту; библиотека не
генерирует идентификаторы и не проверяет наличие файла.

`with_mapping_publication(mapping, publication, issue=None, target_locators=None,
limits=None)` возвращает независимую карту. При переходе staged → published
сохраняются result ID, вхождения, группы и полнота объявленной области, но все
native target locators сбрасываются в unknown. Вызывающий код может передать
новые подтверждённые адреса через `target_locators`; непереданные адреса остаются
неизвестными. Переименование файла само по себе не подтверждает адреса.

С версии 0.9.1 новые адреса устанавливаются до валидации конечной копии:
target может быть известен только по native locator, без модельного узла или
ресурса. В таком случае при смене стадии требуется передать подтверждённый
locator явно; сброс единственного handle отклоняется атомарно. Входная карта
и переданные адреса остаются независимыми от результата.

При rejected/invalidated/attempted/unknown функция убирает текущие targets,
сбрасывает `target_ids=None`, полноту и target-scoped replacements. Исходные
вхождения, source-scoped replacements, диагностика групп и неизвестные поля
сохраняются. `publication_issue` хранит переданную причину отказа, отмены или
утраты актуальности. Исходная staged/published карта не меняется и может
храниться как историческое свидетельство отдельно от текущей карты.

Rejected/invalidated нельзя оживить этой функцией до staged/published:
повторный запуск требует новой карты. Отказ качества, отмена, удаление временного
результата и утрата актуальности отмечаются вызывающим кодом явно. Библиотека
не выполняет файловых операций и не обнаруживает эти события самостоятельно.
Полнота staged не означает окончательной публикации; никакая карта сама по себе
не разрешает существующие политики качества.

## JSON и проверка ссылок

`object_mapping_to_dict(mapping, limits=None)` создаёт независимый JSON-конверт
`{"format":"opendoc.object-mapping","version":1,...}`.
`object_mapping_from_dict(data, limits=None)` читает только эту схему.
Для JSON-текста вызывающий код использует обычные `json.dumps`/`json.loads`;
ограничение байтов и глубины до разбора текста остаётся обязанностью его reader.
Модель проверяет уже разобранное дерево и количество/глубину/размеры данных через
`DocumentLimits` до кодека. Неизвестные поля сохраняются; они не могут затенять
известные поля, `extra` или format/version конверта. Boolean не заменяет версию.

`validate_object_mapping(mapping, source=None, target=None, limits=None)`
проверяет карту и, если переданы снимки, их валидность, anchor/resource references
и соответствие kind замены типу Resource. Scope source/target определяет,
в каком снимке искать ресурс замены. Снимок не передан — его ссылки не
подтверждены этой проверкой; нативные locator и содержание изображения никогда
не проверяются моделью. Регистры карты всегда проверяются на dangling IDs,
повторы и противоречия. Нарушения схемы дают `mapping.invalid` с расположением;
превышение бюджета — `ArtifactLimitError`. Отказ не меняет входные объекты.
Невалидные JSON-значения и циклы дают существующие `ValueError` и JSON-диагностику.

Документный JSON v1/v2, integration v1, прежние отчёты и конструкторы сохранены.
Карта возвращается отдельно либо её JSON-словарь хранится в открытом поле
отчёта/metadata/extra. Такой словарь не получает автоматической валидации карты:
вызывайте явный reader/validator. Отсутствие отдельного поля нельзя подменять
пустой проверенной картой. Новых обязательных зависимостей нет.

## Изменение идентификаторов и адресов

`remap_object_mapping` возвращает независимую карту. `source_nodes`,
`target_nodes`, `source_resources`, `target_resources` — явные словари старый ID
→ новый ID. Stable occurrence ID и группы остаются прежними. `target_locators`
связывает target occurrence ID с новым измеренным `NativeObjectLocator` или
`None` для сброса адреса в unknown. Столкновения anchor ID, неизвестные
occurrence ID и некорректные данные отклоняются атомарно.

Функция не вычисляет адрес из новой позиции узла. После перестановки или нового
экспорта адрес обновляется только по новым измерениям; устаревший native locator
вызывающий код явно сбрасывает или заменяет. Provenance остаётся исходным
свидетельством и автоматически не переписывается. Merge/extract документа не
меняют самостоятельную карту: примените полученные карты ID явно и повторно
проверьте ссылки с актуальными source/target снимками. После удаления объектов
обновите состав групп/реестров и полноту, не оставляя прежние подтверждённые ссылки.

[Тесты](../../tests/test_object_mapping.py) закрепляют собственный ожидаемый JSON,
два цикла, повторные ресурсы, перестановку, перенумерацию, удаление, unknown,
отказы, лимиты и независимость данных. Нативные форматные циклы проверяются
отдельно вызывающим кодом после выпуска пакета.
