# Сноски

`Footnote(id, blocks=[], properties={}, extensions={})` — определение сноски в `DocumentModel.footnotes`. Содержимое состоит из обычных блоков: абзацев, таблиц, изображений и формул. Стили и ресурсы принадлежат документу, их ссылки проверяются так же, как в основном тексте. ID — непустая UTF-8-строка, уникальная среди определений сносок и независимая от ID якорей, ресурсов, стилей и списков.

`FootnoteReference(note_id)` задаёт роль `TextRun` через `set_footnote_reference(run, reference)`. `get_footnote_reference(run)` читает её, `set_footnote_reference(run, None)` снимает. Текст и стиль фрагмента не меняются автоматически. Одновременная внешняя или явная внутренняя ссылка отклоняется обоими setters и валидацией. Якорь на том же фрагменте допустим: он обозначает точку назначения.

## Создание и изменение

`set_footnote(document, note)` добавляет независимую копию определения либо заменяет существующее на его прежнем месте. Кандидат проверяется целиком перед изменением коллекции; ошибка или превышение `DocumentLimits` сохраняет исходное состояние. Можно сначала назначить ссылку, затем этим вызовом добавить недостающую цель, если получившийся документ валиден.

`get_footnote(document, id)` возвращает живое определение либо `None`. Содержимое можно изменить через модель или общий API операций; после правок проверьте документ. Поиск неоднозначного ID даёт `ValueError`. `remove_footnote(document, id)` удаляет только определение, после удаления которого модель остаётся валидной, и возвращает независимый снимок. Сначала снимите или перенаправьте оставшиеся ссылки. Замена коллекции делает прежние положения её элементов устаревшими; повторите обход.

Для взаимных ссылок можно собрать несколько `Footnote` напрямую в модели и затем вызвать `check_document`. Ссылки на себя и между сносками допустимы: библиотека не разворачивает содержимое целей рекурсивно. Неиспользуемые определения тоже допустимы и сохраняются.

Валидация, запись и чтение отвергают отсутствующие цели (`semantic.footnote.missing`), дубли ID (`semantic.footnote.duplicate`), конфликт ролей (`semantic.footnote.conflict`), неверные блоки и неизвестные версии. Диагностика содержит путь поля и ID либо первое расположение дубля.

## Обход и номера

`iter_footnotes(root)` выдаёт `NodeLocation[Footnote]`. Общий обход документа сначала проходит прежние семь коллекций всех секций, затем определения сносок в порядке коллекции, затем их блоки. Путь имеет вид `footnotes[0].blocks[0].content[0]`, вид определения — `"footnote"`. `ModelNode` расширен типом `Footnote`, `NodeKind` — этим новым значением; все прежние варианты сохранены. Поиск элементов, ресурсных ссылок, заголовков и списков, копирование, вставка/замена/удаление, преобразование и извлечение текста включают тела сносок. Поддерево `Footnote` тоже допустимо как корень.

Сноска не является секцией или страницей: `location.section` и `section_index` для её содержимого равны `None`. Инспекция объектов сохраняет `page=None`; геометрия валидируется, но не сравнивается с выдуманными размерами страницы. Пагинация и размещение сносок принадлежат потребителю. Общий текстовый поток и счётчики структурных элементов включают их содержимое после основного документа.

`iter_footnote_references(root)` выдаёт каждое вхождение явной ссылки. `iter_footnote_numbers(document)` сначала проверяет весь документ и возвращает `FootnoteNumber(location, note_id, number)`. Разные ID получают номера с единицы по первому использованию в общем порядке; повторные ссылки сохраняют номер. Ссылки в телах определений тоже учитываются, неиспользуемым определениям номер не назначается. Порядок определений сам по себе не задаёт номер. После изменения структуры расчёт нужно повторить. Номер не заменяет текст фрагмента, не выбирает символ маркера и не моделирует перезапуск по страницам.

## Композиция

`merge_documents` по умолчанию отклоняет совпадающие ID сносок. `conflicts="rename"` сохраняет все определения, включая неиспользуемые, выбирает свободные ID с учётом всех входов и переписывает явные ссылки в секциях и сносках по снимку исходных значений. Результат содержит `DocumentIdMap.footnotes`; прежние аргументы карты сохранены. Ссылки на стили, ресурсы, списки и якоря в телах тоже переписываются. Свободные legacy-свойства не мигрируют.

`footnote_properties` и `footnote_extensions` объединяются по выбранной политике `metadata_conflicts`, с отказом по умолчанию. Операция сохраняет входы и возвращает независимую модель.

`extract_document` включает используемые сноски и их транзитивные зависимости. Внутренняя ссылка из сноски в основное содержимое добавляет исходную секцию цели; ссылка на якорь в другой сноске добавляет целиком её определение. Недостающая цель в частично выбранном определении расширяет его до полного исходного, избегая дублирования перекрывающихся оболочек. Секции и определения располагаются в исходном порядке. Неиспользуемые определения не добавляются, кроме явно выбранного. Политика непрозрачного пакета остаётся явной; стили и ресурсы собираются после замыкания зависимостей. Можно извлечь само определение или расположение внутри его тела.

## Сравнение и неизвестность

Инспекция содержит `footnotes`, `referenced_footnotes`, `semantic_footnote_references` и `metadata.semantic_footnotes` со схемой `opendoc.footnotes-inventory` v1. Прежний счётчик `footnote_references` продолжает считать свободное `footnote_reference_id`.

`object_diff.footnotes` сравнивает определения по ID и отпечатку полного тела, свойств и неизвестных полей. Потеря определения — `LOSS/footnote-loss`, его изменение — `WARNING/footnote-change`; изменение общих свойств/расширений — `WARNING/footnote-collection-change`. Ссылки сопоставляются по отпечатку текста, затем по положению как эвристике; кратность сохранена, неоднозначность отмечена `ambiguous`. Удаление ссылки даёт `LOSS/footnote-reference-loss`, смена её цели, текста, положения или рассчитанного номера — `WARNING/footnote-reference-change`. Диагностика в памяти содержит независимые измерения обеих сторон.

Общий инвентарь объектов и политики содержимого также включают тела сносок; `QualityPolicy` может запрещать зарегистрированные потери. Старый, повреждённый или неподдержанный инвентарь сносок означает `available=False` и `None` для счётчиков потерь/изменений. Он не доказывает отсутствие потерь.

Если в сравнении участвует содержимое сносок, а одна из сторон не имеет совместимого инвентаря сносок, агрегатная сохранность содержимого, объектов и шрифтов тоже неизвестна. Строгие политики текста, объектов, формул и выделений отклоняют такую недоступность; сохранённый старый fingerprint сам по себе её не устраняет. Метаданные инспекции `footnote_content_included` обозначают наличие тел сносок в общем потоке.

## Решение о JSON и совместимости

В памяти определения хранятся в новой необязательной коллекции, без скрытой копии в метаданных. При записи они помещаются в `document.metadata["opendoc.footnotes"]`:

```json
{
  "format": "opendoc.footnotes",
  "version": 1,
  "notes": [{"id": "source", "blocks": [], "properties": {}}],
  "properties": {}
}
```

JSON блоков использует существующую грамматику. Ссылка хранится в свойствах `TextRun` как `{"format": "opendoc.footnote-reference", "version": 1, "note_id": "source"}`. Reader переводит распознанный реестр в `footnotes` и `footnote_properties`, неизвестные поля реестра — в `footnote_extensions`, неизвестные поля определения — в `Footnote.extensions`. Writer восстанавливает их на прежних местах. Расширения не могут подменять зарезервированные поля. Пустой реестр без свойств и расширений нормализуется в отсутствие расширения.

Непромаркированное значение остаётся непрозрачными метаданными. Нельзя одновременно занять этот ключ непрозрачным значением и записать определения: валидация отклоняет конфликт. В памяти назначайте определения через коллекцию/API; сырое распознанное сериализованное значение в метаданных даёт явную ошибку. Setter ссылки сохраняет неизвестные tagged-поля и отказывается перезаписывать непрозрачное значение.

Контракт входит в API библиотеки. Старые аргументы модели сохраняют порядок и defaults; новые коллекция и словари имеют независимые пустые defaults. Пустые новые поля не увеличивают прежний расход лимита узлов. JSON документа по-прежнему записывается как v2 и читается как v1/v2, bags остаются v1; новые реестр и ссылка имеют собственную версию 1. Прежний reader сохраняет эти данные как неизвестные metadata/properties без понимания семантики. `footnote_reference_id`, ресурсы вроде `docx-footnotes` и прикладные форматы автоматически не мигрируют. Неизвестные версии и типы блоков отвергаются.
